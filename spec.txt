Te dejo un **spec técnico completo**, pensado para que puedas crear el repo y empezar a implementar sin tener que redefinir la arquitectura después.

Como base factual importante: AGESIC publica el catálogo de trámites y servicios del Estado en formatos estructurados como CSV/XLSX/XML/JSON; el conjunto incluye descripción, organismo, lugares, requisitos y costos, y se actualiza diariamente. Eso hace viable construir una capa propia de búsqueda y organización sin inventar la información del trámite. ([Catálogo de Datos Abiertos][1])

# TrámitesUY — Technical Specification v1.0

## 1. Visión

**TrámitesUY** es una plataforma open source para ayudar a ciudadanos uruguayos a descubrir qué trámites deben realizar ante una determinada situación de vida.

La diferencia respecto de un buscador tradicional es que el usuario **no necesita saber el nombre del trámite**.

En lugar de buscar:

```text
Transferencia de titularidad de vehículo
```

puede escribir:

```text
Compré un auto usado
```

y el sistema identifica que probablemente se encuentra ante el evento:

```text
COMPRAR_VEHICULO
```

y devuelve los trámites relacionados.

La plataforma no utiliza IA generativa ni depende de APIs de terceros para interpretar la consulta.

El motor de búsqueda será:

```text
determinístico
explicable
auditable
open source
```

---

# 2. Objetivo principal

Transformar esto:

```text
Usuario
   ↓
"No sé qué trámite tengo que hacer"
```

en:

```text
Situación
   ↓
Evento de vida
   ↓
Lista ordenada de trámites
   ↓
Información oficial
```

Ejemplo:

```text
"Compré un auto usado"
```

↓

```text
Evento detectado:
Compra de vehículo
```

↓

```text
1. Verificar situación del vehículo
2. Transferir titularidad
3. Actualizar datos correspondientes
4. Verificar obligaciones tributarias
5. Contratar/actualizar seguro cuando corresponda
```

Cada resultado debe apuntar a la fuente oficial.

---

# 3. Principios del proyecto

El sistema debería seguir estos principios.

### 3.1 La fuente oficial manda

TrámitesUY **no debe convertirse en una base paralela de requisitos legales**.

Los datos objetivos deben venir de fuentes oficiales:

```text
gub.uy
AGESIC
SUCIVE
Intendencias
Ministerios
Entes autónomos
Servicios descentralizados
```

La comunidad puede definir:

```text
qué evento existe
qué términos lo identifican
qué trámites se relacionan
en qué orden deberían mostrarse
```

pero no debería modificar arbitrariamente:

```text
costos
requisitos
direcciones
documentación requerida
horarios
URLs oficiales
```

---

# 4. No usar IA generativa

El MVP no utilizará:

```text
OpenAI
Claude
Gemini
LLMs
RAG
chatbots
```

Tampoco será necesario utilizar embeddings en primera instancia.

La interpretación se realizará mediante:

```text
normalización
tokenización
diccionario de sinónimos
full-text search
BM25/ranking
trigram similarity
pesos manuales
reglas
```

Esto permite explicar cada resultado.

Ejemplo:

```text
Consulta:
"compré un auto usado"
```

Resultado interno:

```text
comprar_vehiculo

Score: 28

+10 "compré" → comprar
+8  "auto" → vehículo
+4  "usado"
+6  combinación comprar + vehículo
```

# 6. Life Event

Un `LifeEvent` representa una situación del ciudadano.

Ejemplos:

```text
comprar_vehiculo
vender_vehiculo
perder_documentos
mudarse
comprar_vivienda
tener_hijo
casarse
fallecimiento_familiar
iniciar_empresa
jubilarse
irse_del_pais
volver_al_pais
```

Ejemplo:

```json
{
  "id": "comprar_vehiculo",
  "name": "Compré un vehículo",
  "description": "Trámites asociados a la adquisición de un vehículo.",
  "category": "vehiculos"
}
```

---

# 7. Procedure

Un `Procedure` representa un trámite oficial.

Ejemplo conceptual:

```json
{
  "id": "transferencia_vehiculo",
  "name": "Transferencia de vehículo",
  "organization": "Organismo correspondiente",
  "description": "...",
  "requirements": [],
  "cost": "...",
  "official_url": "...",
  "source_id": "agesic"
}
```

Los datos del trámite deberían provenir automáticamente del catálogo oficial cuando estén disponibles.

AGESIC publica precisamente información como descripción, organismo, direcciones, requisitos y costos. ([Gub.uy][2])

---

# 8. LifeEventProcedure

Representa la relación:

```text
evento → trámite
```

Ejemplo:

```text
comprar_vehiculo
      ↓
transferencia_vehiculo
```

Debe contener metadata adicional.

```json
{
  "life_event": "comprar_vehiculo",
  "procedure": "transferencia_vehiculo",
  "order": 2,
  "required": true,
  "condition": null
}
```

# 9. Casos condicionales

No todos los trámites aplican siempre.

Ejemplo:

```text
Compré un auto
```

podría depender de:

```text
nuevo/usado
departamento
persona física/jurídica
procedencia
tipo de vehículo
```

La relación debe poder guardar condiciones.

Por ejemplo:

```json
{
  "event": "comprar_vehiculo",
  "procedure": "procedure_xyz",
  "conditions": {
    "vehicle_condition": ["used"]
  }
}
```

Más adelante puede evolucionar hacia un pequeño rule engine.

# 10. Event Keywords

Cada evento tendrá términos relacionados.

Ejemplo:

```yaml
event: comprar_vehiculo

keywords:

  actions:
    comprar: 10
    compre: 10
    adquiri: 10
    adquirir: 8

  entities:
    auto: 8
    coche: 8
    vehiculo: 8
    automovil: 8

  modifiers:
    usado: 3
    nuevo: 2
    cero_km: 3
```

No conviene guardar únicamente strings.

Conviene diferenciar:

```text
ACTION
ENTITY
MODIFIER
CONTEXT
```

Porque permite desarrollar reglas después.

# 13. Sinónimos

Tabla:



---

# 14. Importancia de ACTION + ENTITY

Esta será probablemente la regla más importante del buscador.

Porque:

```text
compré un auto
vendí un auto
perdí la libreta del auto
```

contienen:

```text
auto
```

pero representan eventos totalmente diferentes.

Por eso:

```text
ACTION + ENTITY
```

debería recibir un bonus.

Ejemplo:

```text
comprar + vehiculo
```

↓

```text
comprar_vehiculo +15
```

Mientras:

```text
vender + vehiculo
```

↓

```text
vender_vehiculo +15
```

---

# 15. Motor de scoring

Propuesta inicial:

```text
score =
keyword_score
+ phrase_score
+ action_entity_score
+ text_search_score
+ trigram_score
- negative_score
```

Ejemplo:

```text
"compre un auto usado"
```

Para:

```text
comprar_vehiculo
```

podría producir:

```text
comprar       +10
vehiculo      +8
usado         +3
comprar+vehiculo +15

total = 36
```

Para:

```text
vender_vehiculo
```

quizás:

```text
vehiculo +8
usado    +1

total = 9
```

# 16. Penalizaciones

También debe poder haber keywords negativas.

Ejemplo:

```yaml
event: comprar_vehiculo

negative_keywords:
  vender: -15
  vendi: -15
```

Así:

```text
"vendí mi auto"
```

no aparece accidentalmente como compra.

# 20. Confidence

El motor debe devolver:

```json
{
  "event": "comprar_vehiculo",
  "score": 36,
  "confidence": 0.93
}
```

Pero `confidence` no debería ser una probabilidad matemática falsa.

Podría normalizarse contra los resultados competidores.

Ejemplo:

```text
top1 = 36
top2 = 9
```

Alta confianza.

Pero:

```text
top1 = 22
top2 = 20
```

consulta ambigua.

---

# 21. Estrategia de selección

Ejemplo:

```text
confidence >= 0.75
```

↓

Abrir directamente evento.

```text
0.40 - 0.75
```

↓

Mostrar:

```text
¿Te referías a...?
```

con tres opciones.

```text
<0.40
```

↓

Mostrar categorías relacionadas.

# 26. Nunca borrar inmediatamente

Supongamos que un trámite desaparece del dataset.

No hacer:

```sql
DELETE procedure
```

automáticamente.

Usaría:

```text
status = inactive
```

y almacenaría:

```text
first_seen_at
last_seen_at
deactivated_at
```

Esto permite detectar problemas de la fuente.

# 27. Historial

La fuente oficial indica que el dataset actual no representa el histórico. ([Gub.uy][2])

Por eso TrámitesUY podría crear **su propio historial técnico de cambios**.

Ejemplo:

```text
procedure_version
```

con:

```text
procedure_id
version
payload
valid_from
valid_until
hash
```

Así podrías saber:

```text
17/09:
costo cambió de X → Y
```

Esto tiene mucho valor.

# 28. Hash de contenido

Cada trámite puede tener:

```text
SHA256(normalized_payload)
```

Si:

```text
previous_hash == current_hash
```

↓

no hay cambios.

Si cambia:

```text
crear nueva version
```

# 90. Filosofía

La idea conceptual que yo mantendría durante todo el desarrollo sería:

> **El ciudadano conoce su problema; el Estado conoce el trámite. TrámitesUY conecta las dos cosas.**

Y técnicamente:

```text
natural language
       ↓
normalización
       ↓
clasificación determinística
       ↓
evento de vida
       ↓
trámites oficiales
```

Eso es suficientemente simple para poder construirlo, suficientemente útil como para que alguien realmente lo use y suficientemente extensible como para que termine siendo un proyecto open source serio.

Además, Uruguay tiene hoy más de **2.600 datasets abiertos publicados por más de 70 organizaciones**, así que una vez que la arquitectura de ingestión esté bien hecha, el proyecto podría incorporar progresivamente otras fuentes oficiales sin cambiar su esencia. ([Gub.uy][3])

**Para arrancar yo implementaría solo tres cosas: ingestion de AGESIC, modelo `LifeEvent → Procedure` y el buscador determinístico.** Todo lo demás debería crecer alrededor de ese núcleo.
